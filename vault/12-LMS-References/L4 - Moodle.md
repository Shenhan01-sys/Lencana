# L4 - Moodle

**Part of:** [[12-LMS-References/00 - Hub LMS References]]
**Source:** references/moodle @ e68a1418b (`github.com/moodle/moodle`, `main`, commit 2026-09-16, read 2026-09-26)

**Summary:** Moodle is a reference for **bookkeeping**, not for trust. What it does well — which activity produced which number, who last touched it, whether it counted — it does by storing more rows and serving its own JSON from its own URL. Nothing in `badges/` is signed; nothing is anchored. Its **gradebook** (§2) and **payment subsystem** (§3) are the two structures we have no equivalent of.

> **Before any path below.** At this SHA the whole web-accessible tree lives under `public/` — there is no top-level `course/`, `mod/`, `enrol/` or `badges/`. `git status` is clean and `git ls-files` counts 62,675 tracked paths, so the checkout is complete, not truncated. Citations are `references/moodle/<path>:<line>`.

## 1. Composition: course → section → activity module

| level | table (`references/moodle/public/lib/db/install.xml`) | what it holds |
|---|---|---|
| course | `course` (`:70`) | `format`, default `topics` (`:80`); `enablecompletion` (`:102`); `showcompletionconditions` (`:107`) |
| section | `course_sections` (`:382`) | `sequence` — a **text column listing course-module ids in order** (`:390`); per-section `availability` JSON (`:392`) |
| activity | `course_modules` (`:324`) | `course` / `module` / `instance` / `section` (`:327-330`) |

`course_modules` is a join, not content: `module` points at `modules` (`:816`, the registry of installed activity types) and `instance` at a row in **that plugin's own table**. A quiz lives in `quiz` (`references/moodle/public/mod/quiz/db/install.xml:7`), an assignment in `assign` (`references/moodle/public/mod/assign/db/install.xml:7`); `course_modules` holds only cross-cutting policy — visibility, grouping, completion, restrictions.

**Where content lives.** Structured text is DB columns (`course_sections.summary`, `quiz.intro`); binaries are not. Uploads go to a content-addressed pool — `files`, commented "content is stored in sha1 file pool", with `contenthash` (`install.xml:2656`, `:2659`). Same instinct as our `rubricHash`/`manifestHash` split, applied to blobs instead of policy.

**The `mod_*` contract** is naming-convention based, not interface based, and documented in-tree at `references/moodle/public/mod/README.txt:9-31`: each module ships `mod_form.php`, `version.php`, `db/install.xml`, `index.php`, `view.php`, `lib.php`, and implements `modulename_add_instance()`, `modulename_user_complete()`, `modulename_user_outline()`, `modulename_cron()`. **23** modules have a `version.php` here (counted). Per-activity data is assembled into `cm_info` (`references/moodle/public/course/classes/cm_info.php:187`) by `get_fast_modinfo()` (`references/moodle/public/lib/modinfolib.php:58`) in three documented stages — cacheable, user-dependent, view-only (`cm_info.php:36-46`). Layout is a separate axis: **4** formats (`topics`, `weeks`, `singleactivity`, `social`), selected by `course.format`.

**Quiz** = settings (`quiz`) + ordered slots (`quiz_slots:76`) + attempts (`quiz_attempts:148`: per-attempt `sumgrades`, `state` ∈ `inprogress|overdue|finished|abandoned`) + one collapsed row per learner in `quiz_grades:178`, chosen by `quiz.grademethod` (highest / average / first / last, `:23`). Per-question marks are not in `mod_quiz` — they live in the shared engine (`question_attempts`, `install.xml:1595`). **Assignment** = `assign` + `assign_submission` (`mod/assign/db/install.xml:59`: "metadata … does not include the submission itself which is stored by plugins") + `assign_grades` (`:83`, `grader` beside `grade`). Grading is a **state machine**, not a boolean: `notmarked → inmarking → readyforreview → inreview → readyforrelease → released` (`references/moodle/public/mod/assign/locallib.php:64-69`), with blind marking, marker allocation and multi-marking as columns.

## 2. Completion, restrictions and the gradebook

**Per activity.** `course_modules.completion` is three-valued — 0 off, 1 manual tick, 2 automatic by rules (`install.xml:340`) — beside `completionview`, `completionpassgrade` (`:344`), `completionexpected`. Automatic state comes from `completion_info::internal_get_state()` (`references/moodle/public/lib/completionlib.php:688`): core rules, then the plugin's own via `activity_custom_completion`, then **all AND-ed** (`:724-737`). States are `INCOMPLETE 0 / COMPLETE 1 / COMPLETE_PASS 2 / COMPLETE_FAIL 3` (`:73-89`) — *"did it and failed"* is first-class, which is why a learner can see both. One row per learner per activity in `course_modules_completion` (`install.xml:365`), with `overrideby` recording a manual override.

**Per course.** Not a roll-up: a separate `course_completion_criteria` table (`install.xml:162`) over **eight** pluggable types — self, date, unenrol, activity, duration, grade, role, course (`references/moodle/public/completion/criteria/completion_criteria.php:42-78`) — aggregated ALL or ANY. The result lands in `course_completions` (`install.xml:203`), keeping `timeenrolled`, `timestarted` and `timecompleted` as three separate facts.

**Restrictions** are one JSON boolean tree in a text column on both section and activity (`install.xml:392`, `:346`), shaped `{"op":"&","showc":[…],"c":[…]}` (`references/moodle/public/availability/classes/info.php:595`), evaluated by `info::is_available()` (`:175`). Six condition plugins ship (`completion`, `date`, `grade`, `group`, `grouping`, `profile`); the `grade` one gates on a grade-item id with min/max (`references/moodle/public/availability/condition/grade/classes/condition.php:92`), so "chapter 4 opens when item 12 ≥ 70" is data, not code.

**The gradebook — the concept our UI lacks.** `grade_items` (`install.xml:2020`) are the columns; one activity may own several. `grade_grades` (`:2069`) is one row per (item, learner) and holds the provenance: `rawgrade`/`rawgrademax`/`rawgrademin` frozen *when the grade was stored*, `finalgrade` cached after aggregation, `usermodified` = "the userid of the person who last modified this grade" (`:2078`), `overridden` (`:2084`), `excluded` (`:2085`), `feedback`, and the two that matter most — `aggregationstatus` ∈ `unknown|dropped|novalue|used` (`:2092`) and `aggregationweight`, "the percent this item contributed to the aggregation" (`:2093`). Every change is appended to `grade_grades_history` (`:2219`). The learner report renders exactly this and its columns are pinned by an acceptance test — `Grade item | Calculated weight | Grade | Range | Percentage | Contribution to course total` (`references/moodle/public/grade/report/user/tests/behat/user_view.feature:60-71`), including `Test quiz one | 0.00 %( Empty ) | - | 0–100 | - | 0.00 %`: an ungraded item shows as *empty*, never zero. `fill_contributions_column()` (`references/moodle/public/grade/report/user/classes/report/user.php:989`) walks the parent chain multiplying the normalised value by each ancestor's weight; every row keeps a `cmid` (`:544`) so the number links back to the activity that produced it.

**Lencana's position.** `web/src/score.ts:29` already models `{name, weight, raw, earned}` per component and `web/src/score.ts:40` refuses a number while the verdict is `BELUM_LENGKAP`, with `missing[]` (`:80-95`) as the gap list — the same instinct as `aggregationstatus = novalue`. Absent is **persistence and history**: `computeScore()` is pure over evidence in `localStorage` (`web/src/progress.ts:17,48`), so there is no row, no `usermodified`, no trail, and the learner never sees the weight × contribution arithmetic `formatScore()` can already print. Worth taking is the shape "one stored row per (component, learner) with raw, weight, contribution, status, who set it" — not their schema, not their markup ([[11-Refactoring/RF4 - Learning Surface Target Shape]]).

## 3. Enrolment, and what paying for a course looks like

`enrol_plugin` is the abstract base and "the main source of documentation" (`references/moodle/public/lib/enrollib.php:1873-1881`): `enrol_get_plugin()` (`:142`) resolves by name, `enrol_user()` (`:2112`) writes the participation row, `enrol_page_hook()` (`:2790`) lets a plugin draw its own enrolment UI, `can_self_enrol()` (`:2802`) gates it. **13** plugins ship, each with a `version.php` (counted): `category, cohort, database, fee, flatfile, guest, imsenterprise, ldap, lti, manual, meta, paypal, self`. Two tables carry everything: `enrol` (`install.xml:255`) = one *instance* of a plugin on one course; `user_enrolments` (`:302`) = one participation row, unique per (`enrolid`,`userid`) — "Only one enrolment per plugin allowed" — with `timestart`, `timeend`, `status`. **An enrolment is a first-class, time-bounded, attributable object**; we have no such record (§6).

**Paid enrolment.** The plugin the brief calls `enrol/payment` is `enrol_fee` at this SHA (`references/moodle/public/enrol/fee/version.php:29`). It does not touch money; it delegates through three callbacks (`references/moodle/public/enrol/fee/classes/payment/service_provider.php`): `get_payable()` returns `(amount, currency, accountId)` off the enrol instance (`:43-49`), `get_success_url()` (`:58-64`), and `deliver_order()` (`:73-92`) simply calls `$plugin->enrol_user($instance, $userid, $instance->roleid, $timestart, $timeend)`. Price and currency are per-instance columns (`enrol.cost` `install.xml:270`, `.currency` `:271`); the receiving account is chosen per instance (`customint1`, `references/moodle/public/enrol/fee/classes/plugin.php:346`).

**Who receives the money.** A `payment_accounts` row (`install.xml:4524`) bound to a `contextid` — the account belongs to a site or category, so whoever manages that context manages the merchant record. Each account holds `payment_gateways` rows (`:4540`) with that gateway's own `config` blob (PayPal client id + secret). **There is no author/platform split anywhere**: one amount, one account, one merchant. Our `SettlementSplit` + `platformBps` has no counterpart ([[02-Contracts/C3 - SettlementSplit]]).

**Confirmation is server-side and refuses a client-supplied price.** `transaction_complete::execute()` (`references/moodle/public/payment/gateway/paypal/classes/external/transaction_complete.php:61`) recomputes the expected amount from `get_payable()` plus surcharge (`:72-78`), fetches the order from PayPal, compares `amount.value` and `currency_code` against **its own** number (`:92`), and only then captures, records and delivers (`:94-108`). The doc comment gives the reason: "This function does not take cost as a parameter as we cannot rely on any provided value" (`:54`). Ledger: `payments` (`install.xml:4555`) holds `component/paymentarea/itemid/userid/amount/currency/accountid/gateway` and nothing else — `save_payment()` inserts it (`references/moodle/public/payment/classes/helper.php:273`, insert at `:288`); the gateway keeps its own reference separately (`paygw_paypal.pp_orderid`, `references/moodle/public/payment/gateway/paypal/db/install.xml:7-11`).

**Refunds are not expressible.** `grep -i refund` over `public/payment/` and `public/enrol/fee/` returns **zero** matches, and `payments` has no status/void/refund column. A paid enrolment can be removed or expire (`enrol/fee/classes/task/process_expirations.php`), but the money is not reversed by Moodle — that is out-of-band at the gateway.

**Self-enrolment and keys.** `enrol_self::can_self_enrol()` (`references/moodle/public/enrol/self/lib.php:275`) requires: not a guest, not already enrolled (`:284`), instance open, and `enrol/self:enrolself` in the course context (`:296`). The key is a shared secret in `enrol.password` (`install.xml:269`), auto-generated as 20 random characters when the site requires one (`lib.php:394-395`), optionally checked against the password policy (`:766-775`), and **doubled as a group key** — with `customint1` set the same string also places the learner in the matching group (`:193-201`).

## 4. Badges — precisely

| question | Moodle at e68a1418b |
|---|---|
| **OB version** | **2.0 / 2.1 only.** `OPEN_BADGES_V1 = 1`, `V2 = 2`, `V2P1 = 2.1` (`references/moodle/public/lib/badgeslib.php:111-117`); `@context` is the literal `https://w3id.org/openbadges/v2` (`:122`); default with no backpack is `OPEN_BADGES_V2` (`:1121-1123`). **No V3 constant exists.** A class comment does say "achievement credential from OBv3.0 onwards" (`references/moodle/public/badges/classes/achievement_credential.php:25`), but that class is a DB-row holder and every emitter writes v2 — the naming follows the spec's *rename*, not its version. |
| **Assertion contents** | `@context`, `type: Assertion`, `id` (the site's own JSON URL), `recipient`, `verify`, `issuedOn`, nested `badge`, `evidence` (a `/badges/badge.php?hash=` URL), optional `expires`, `tags` — `references/moodle/public/badges/classes/local/backpack/ob/v2p0/assertion_exporter.php:55-92`. Recipient is `type: email`, always `hashed: true`, identity `sha256$` of **email + a site-wide salt** (`…/v2p0/recipient_exporter.php:48-57`). The nested BadgeClass carries `criteria` as **prose**: `markdown_badge_criteria()` regenerated from live DB rows on every request (`…/v2p0/badge_exporter.php:85`, `:135-148`; `references/moodle/public/badges/classes/badge.php:882`). |
| **Who signs it** | **Nobody.** `verify.type` is hard-coded `'hosted'` with the comment `// Signed is not implemented yet.` (`assertion_exporter.php:62`). Validity = "this URL, on the issuer's server, still says so". The identifier `uniquehash` is `sha1(rand() . $userid . $this->id . $now)` (`badge.php:437`) — an unkeyed label, not a signature, not checkable offline. The PNG is *baked* with the assertion JSON in an `iTXt` chunk keyed `openbadges` (`badgeslib.php:766-768`): the **pointer** travels with the image, the **proof** does not. |
| **Revocation expressible?** | **Yes — as mutation, not as state.** Revoking deletes the row: `award_manager::process_manual_revoke()` runs `$DB->delete_records('badge_issued', …)` (`references/moodle/public/badges/classes/award_manager.php:76`, delete at `:100`). The endpoint then sees the hash is gone (`helper::assertion_exists()` queries `badge_issued`, `references/moodle/public/badges/classes/local/backpack/helper.php:55`), swaps in `revoked_assertion_exporter` (`…/ob_factory.php:44`) and serves `{'id': …, 'revoked': true}` (`…/v2p0/revoked_assertion_exporter.php:44-48`) with `HTTP/1.0 410 Gone` (`references/moodle/public/badges/json/assertion.php:45-46`). Machine-readable **only while the issuer's server is up and honest**, and the deletion leaves no distinction between "never issued" and "issued then revoked". |
| **Blockchain anchored?** | **No.** `grep -iE "blockchain|verifiable credential|statusList|data-integrity|Ed25519|proof"` over `public/badges/` → **zero matches**. Repo-wide hits are all vendored code (`lib/aws-sdk` Managed Blockchain clients, `lib/tcpdf` bit-packing, `lib/webauthn` DER bit strings, a `.fa-ethereum` CSS class) — none in the badge path. |

**Against ours.** Lencana issues OB 3.0 in a VC 2.0 envelope — `type: ['VerifiableCredential','OpenBadgeCredential']`, `@context = [VC v2, OB v3]` (`signer/src/credential.js:68`; `signer/src/context.js:18,30`) — with a `Result` object per OB 3.0 (`credential.js:103-111`), `validUntil` rather than `expirationDate` (`:72`), and a **signed** document (DataIntegrityProof / `eddsa-rdfc-2022`; `signer/package.json:5`, asserted by `signer/scripts/check.js:63`). Recipient is an on-chain address bound by `holderOf()` and the soulbound artefact, not a salted email (`credential.js:78-84`). Status is **two** Bitstring Status List entries — revocation *and* suspension — both derived from chain state (`credential.js:111-114`; `signer/src/statusList.js:91,130,138`). The credential prints the **rubric version into itself**: `criteria: "<criteria> [rubrik <rubricRef>]"` (`signer/scripts/issue.js:241`). Verification is free, wallet-less, against chain state through a public client (`web/src/verify.ts:191-192`); anchoring is on BAS, the EAS fork. Three differences are load-bearing: our criteria are a **hash commitment** where theirs are regenerated prose; our revocation is **readable from a ledger the issuer cannot edit** where theirs is a row deletion behind the issuer's own URL; and suspension is a distinct expressible state where Moodle has only issued-or-gone ([[Concepts/Issuer Delisted vs Revoked]]).

## 5. What Lencana has that Moodle does not

*By design* — things Moodle's model cannot express:

- **Issuer-owned rubric committed into the credential.** Their `criteria` narrative is rebuilt from the live DB at export time (§4); ours is `rubricHash = keccak256(canonicalPolicy(manifest))` (`web/src/manifest.ts:102`) printed into the signed document (`signer/scripts/issue.js:241`), so a post-issuance rubric edit is detectable rather than silent ([[Concepts/rubricHash and manifestHash]]).
- **A third-party agent signs via EAS delegation while the platform fronts gas** — `signDelegatedAttestation()` (`signer/src/delegation.js:108`), `relayDelegated()` (`:215`); the platform never holds the issuer key ([[04-Signer-Service/S4 - Delegated issuance]]). Moodle has one issuer: the site.
- **Free, wallet-less public verification against chain state**, not against the issuer's uptime (`web/src/verify.ts:191-192`).
- **x402 paid machine verification settled through a split contract** with a per-payment `ref` replay guard and a `platformBps` that can only be lowered ([[04-Signer-Service/S6 - x402 paid verification]], [[11-Refactoring/RF5 - Enrollment and the Paid Path]]). Theirs is one merchant, one amount, no split (§3).
- **Grading authority outside the platform.** `computeScore()` holds no institutional constants and refuses to publish a number when weights do not sum to 100 (`web/src/score.ts:71`, `:112-121`; [[05-Course-Content/K4 - Scoring without the platform deciding]]). In Moodle the site *is* the institution, so it never had to solve this.

*By code* — verified present in `app/`: the typed content model with six interaction kinds and a DOM-free auditor (`web/src/content.ts:26,34`), the manifest registry (`web/src/manifest.ts`), the three-verdict scorer (`web/src/score.ts:39-40`), the delegated signer (`signer/src/delegation.js`), the two status lists (`signer/src/statusList.js`), four deployed contracts (`contracts/{CredentialResolver,SoulboundCert,SettlementSplit,DemoCourseToken}.sol`).

## 6. What Moodle has that Lencana lacks

**Design gaps** — never decided; each needs a decision, and some should stay "no".

| Moodle structure | evidence | our state |
|---|---|---|
| An **enrolment record**: time-bounded, attributable, one per plugin per learner | `user_enrolments` (`install.xml:302`) | none — no table, no type, no route |
| **Gradebook persistence + history**: raw/final, weight, contribution, `used\|dropped\|novalue`, who modified | `grade_grades` (`install.xml:2069-2093`), `grade_grades_history` (`:2219`) | `Component` computed then discarded (`web/src/score.ts:29`) |
| **Restriction rules as data**, gating a chapter on another item's grade or completion | `availability` tree (`install.xml:346,392`), grade condition (`condition.php:92`) | course-level `prereqCourseId` only (`web/src/content.ts:100`) |
| **Completion state ≠ pass state** (`COMPLETE_FAIL`), per-criterion course completion | `completionlib.php:84-89`; `completion_criteria.php:42-78` | `done: boolean` (`web/src/progress.ts:22`) |
| **Assignment workflow**: draft→submitted, notmarked→released, blind marking, second marker | `assign_submission` (`mod/assign/db/install.xml:59`); `locallib.php:64-69` | a local `draft` string, no states |
| **Roles beyond learner/issuer** — 8 archetypes incl. non-editing teacher, manager, coursecreator | `accesslib.php:2204-2238` | none |
| **Payment accounts bound to a context**, so an institution owns the merchant record | `payment_accounts.contextid` (`install.xml:4524`) | publisher named in the manifest, no account object |

Rows 1–2 are the highest value: RF5 already assumes an enrolment record exists, and row 2 is the missing concept named in [[11-Refactoring/RF4 - Learning Surface Target Shape]]. Rows 5–7 (blind marking, second marker, manager roles, publisher onboarding) are candidates for a permanent "no" — publisher onboarding is already on the limits sheet ([[08-Results/01 - Evidence and Limits]]).

**Implementation gaps** — decided, not built, or built and not wired. All re-verified from `app/` on 2026-09-26.

- **No enrolment handler at all.** `btnEnroll` is declared at `web/src/i18n.ts:189`, translated at `:665` (`'Start Course'`) and `:1238` (`'Mulai Belajar'`), referenced nowhere else — `findstr /s /n /c:"btnEnroll" web\src\*.ts web\index.html` returns exactly those three lines ([[11-Refactoring/RF1 - Consumer Readiness Audit]] 1.1).
- **No payment step in the learner flow.** The browser-side x402 is a **timer-driven simulation**: `simulateX402Batch()` writes `'402 CHALLENGE'`, `'SIGNED (0.0005 tBNB)'`, `'SETTLED'`, `'200 OK (118ms)'` from three `setTimeout`s at 350/850/1350 ms and makes no network call (`web/src/main.ts:1003-1070`).
- **No demo-vs-real separation.** Simulated numbers sit beside real chain reads on one screen with no marker (RF1 1.5, 1.8). Moodle's seam is explicit: `paygw_paypal` config carries `environment == 'sandbox'` and branches on it (`transaction_complete.php:71-72`).
- **No mentor / assistant / non-editing-teacher surface.** `findstr /s /i /n /c:"mentor"` over `web/src/main.ts`, `web/src/i18n.ts`, `web/index.html` → 0 matches (RF1 1.6).
- **Progress is `localStorage` only**, documented as *not evidence* (`web/src/progress.ts:1-13`, `:17,48`) — correct as a trust claim, but it leaves nothing for a gradebook row to reference.
- **Learning surface not linked from the main navigation.** Nav is Home / Courses / AI Assessment / Verifier / Portfolio / Agent Hub (`web/index.html:44-49`); `#/learn` occurs in that file only inside a comment at `:581`. 34 pages of content are one typed URL from invisible (RF1 1.3, [[03-Frontend/FE6 - Quirks and open defects]]).
- **Wallet-connect is the only identity path** — `eth_requestAccounts` (`web/src/main.ts:504`) plus a hand-typed address field for reading one's own credentials (`web/src/lms.ts:338`). Moodle separates *authentication* (`auth/*`) from *enrolment* (13 plugins) from *identity in a credential*; we collapse all three into "connect a wallet".

## 7. What we deliberately do not take

- **The plugin API** — 23 `mod_*` + 13 `enrol_*` + 4 formats + 6 availability conditions + 8 badge criteria + 9 completion criteria, resolved by naming convention (`mod/README.txt:21-31`). It only pays off with third-party authors; we have one publisher and a deadline, and a convention-based plugin system is invisible to `npm run probe`. Our equivalent is a discriminated union the auditor can check (`web/src/content.ts:34`).
- **A server-rendered admin surface.** Their authoring, grading and configuration are PHP pages behind login; Lencana is static, hash-routed and DOM-free-typed so the same content module runs in Node for probe ([[03-Frontend/01 - Frontend]]). Taking their shape means taking a server, sessions, and a second place where a claim can be made without evidence.
- **SCORM / IMS packaging** (`public/mod/scorm`, `public/mod/imscp`) — a container format for content we could then neither hash, audit nor re-rubric; it conflicts directly with `manifestHash`.
- **Hosted verification as the validity model.** `verify.type = 'hosted'` makes the issuer's uptime and honesty the definition of truth — the sentence this vault has refused since D23 ([[00-Overview/03 - Decisions]]).
- **Salted-email recipient identity** (`recipient_exporter.php:48-57`) — depends on a secret the verifier cannot obtain, so it proves nothing to a third party; ours is a public address bound on chain.
- **Platform-side grade override.** `grade_grades.overridden` / `.excluded` and `course_modules_completion.overrideby` let the institution overrule the evidence. Sensible in a real LMS, fatal here: our number must be reproducible from the issuer's rubric plus the evidence, or `rubricHash` commits to nothing.
- **The `enrol` table's spare columns** — `customint1..8`, `customchar1..3`, `customtext1..4` (`install.xml:273-289`). One schema for thirteen plugins is why `customint1` means "payment account" in `enrol_fee` and "group key" in `enrol_self`.

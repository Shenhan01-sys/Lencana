# L5 - Open edX

**Part of:** [[12-LMS-References/00 - Hub LMS References]]
**Source:** `references/edx-platform` @ `303f778` (`github.com/openedx/edx-platform`, `master`, commit `303f778c16b7547956a4106d66503b79a56a7db8`; shallow clone, gitignored, so nothing here is reproducible from `app/`)

**Summary:** One content primitive — the XBlock — from course down to a single video. The two structural ideas worth studying are *completion as a service rather than a column* and *grading policy as a hashable document*. The two business-process ideas are *what is sold is a mode, not a course* and *a certificate is checked by a public URL that only the issuer's own database can answer* — the exact property we exist to remove. **ORA's engine is not in this clone**; what is here is its staff-grading bridge, which is enough to read its data model but not its workflow.

## 1. How it is structured

| level | class | path |
|---|---|---|
| course | `CourseBlock` | `references/edx-platform/xmodule/course_block.py:1072` |
| section (= "chapter") | `SectionBlock(HighlightsFields, SequenceBlock)` | `xmodule/seq_block.py:992`, highlights `:985-990` |
| subsection | `SequenceBlock` | `xmodule/seq_block.py:239` |
| unit | `VerticalBlock` | `xmodule/vertical_block.py:55` |
| component | `UnitBlock` / `WrapperBlock` / leaf blocks | `xmodule/unit_block.py:18`, `xmodule/wrapper_block.py:13` |

The hierarchy is **enforced on import**, not by convention: `xmodule/modulestore/xml_importer.py:1330-1341` rejects a course with non-`chapter` children, a chapter with non-`sequential` children, a sequential with non-`vertical` children. `chapter` is still the wire name for what the UI calls a section — `lms/djangoapps/course_home_api/outline/views.py:564` branches on it.

**Two processes, one repo.** `manage.py {lms|cms}` (`manage.py:3`) picks `lms/envs/` or `cms/envs/`. Studio writes a *draft* branch, the LMS reads the *published* branch, and publishing copies the subtree between them (`xmodule/modulestore/split_mongo/split_draft.py:370-390`; unpublish `:392`). Author verbs are `make_public` / `republish` / `discard_changes`, and a *pure* publish is a different permission from an edit (`cms/djangoapps/contentstore/xblock_storage_handlers/view_handlers.py:217-229`). Every block records who edited it and who published it (`xmodule/modulestore/edit_info.py:11-57`).

**Policy is declared once and inherited down.** `InheritanceMixin` (`xmodule/modulestore/inheritance.py:33`) declares `graded` (`:36`), `start`/`due` (`:41`,`:46`), `group_access` (`:83`), `showanswer` (`:88`), `max_attempts` (`:145`), `graceperiod` (`:79`); a component that does not set them inherits its ancestor's value. So "this subsection is graded" is one write, not one per problem.

**Completion is a service.** Each block declares a `completion_mode`: `AGGREGATOR` for containers (`seq_block.py:62`, `unit_block.py:32`), `COMPLETABLE` for a video (`xmodule/video_block/video_block.py:128`), `EXCLUDED` for a discussion (`xmodule/discussion_block.py:46`). Counts live in the external `edx-completion` app (`requirements/edx/base.txt:441`), are rolled up per level (`course_home_api/outline/views.py:550-578`) and only over types that can be completed at all (`:648-659`).

**A unit is complete only when its *assignments* are.** `VerticalBlock.is_block_complete_for_assignments` (`vertical_block.py:307`) returns `True` only if every assignment child is complete, `False` if any is not, and **`None` if there are no assignments** — a reading-only unit therefore renders no past-due and no complete marker (`:139` consumes the three-valued result). "Assignment" = `graded and has_score and weight > 0` (`xmodule/util/misc.py:106-115`).

**Navigation is one persisted integer plus a derived URL.** `position` is `Scope.user_state`, 1-indexed, with a comment admitting it can no longer be fixed (`seq_block.py:64-66`), set by a JSON handler (`:305-318`) or from the URL (`:263-273`). The subsection hands its item list `graded` and `complete` per unit (`:807`, `:815-816`); "resume" is one URL from the last completed block, falling back to the start block when there is no completion data (`course_home_api/outline/views.py:286-294`, serialised as `{has_visited_course, url}` at `outline/serializers.py:137-143`).

**What an author may add to a unit** is a closed list plus a plugin surface: `COMPONENT_TYPES = html, video, problem, itembank, library_v2, discussion, openassessment, drag-and-drop-v2` (`cms/djangoapps/contentstore/views/component.py:49-58`); every other registered XBlock becomes "advanced" automatically (`:62`).

## 2. Assessment

**Problem block** (`xmodule/capa_block.py:141`) — `attempts` / `max_attempts` (`:186-197`); a per-problem `grading_method` of LAST / FIRST / HIGHEST / AVERAGE (`:94-101`, field `:198`); a `showanswer` policy with thirteen timings including `after_all_attempts_or_correct` and `correct_or_past_due` (`:75-91`, field `:231`); per-student randomisation (`:105-112`, field `:272`); `weight` (`:320`); a cooldown between attempts (`:314`). **Every attempt is kept**, not just the last: `correct_map_history` (`:296`), `student_answers_history` (`:299`), `score_history` (`:305`). The response-type engine is external — tests patch `xblocks_contrib.problem.capa.responsetypes.NumericalResponse` (`xmodule/tests/test_capa_block.py:1634`), i.e. `xblocks-contrib==1.0.6` (`requirements/edx/base.txt:1303`).

**Course arithmetic is data.** `grading_policy` is a course field (`course_block.py:390`), default = four assignment types with `min_count` / `drop_count` / `weight` plus `GRADE_CUTOFFS: {Pass: 0.5}` (`xmodule/course_metadata_utils.py:22-55`). Two graders compose: `WeightedSubsectionsGrader` (`xmodule/graders.py:238`) multiplies sub-graders by weight and deliberately **does not normalise** — weights above 1 are extra credit (`:250-252`); `AssignmentFormatGrader` (`:293`) drops the N lowest (`total_with_drops`, `:349-368`) and inserts placeholder zeros up to `min_count` (`:300-302`). Both return one three-key contract — `percent`, `section_breakdown`, `grade_breakdown` (`graders.py:204-230`) — and the learner/staff-facing row is `{attempted, category, label, module_id, percent, score_earned, score_possible, subsection_name}` (`lms/djangoapps/grades/rest_api/serializers.py:35-46`).

**Grades are persisted with their provenance.** `PersistentSubsectionGrade` (`lms/djangoapps/grades/models.py:295`) stores `earned_all` / `possible_all` / `earned_graded` / `possible_graded` (`:345-348`), `first_attempted` (`:353`) and `visible_blocks` (`:356`) — the exact set of blocks visible *to that learner* when the number was computed. `PersistentCourseGrade` (`:558`) stores `percent_grade`, `letter_grade`, `passed_timestamp` (`:593-597`), `course_version` and **`grading_policy_hash`** (`:590`).

**`grading_policy_hash` is their rubricHash, and it is not the same thing.** `b64(sha1(json.dumps(course.grading_policy, sort_keys=True, separators=(',',':'))))` (`lms/djangoapps/grades/transformer.py:87-97`), read through the block structure (`course_data.py:79-88`) and re-emitted on every grade change (`grades/models.py:719-733`). Two differences matter: it commits to **weights and cutoffs only** — not rubric criteria, not answer keys, not per-assessment pass marks — and it is recorded, not enforced. I searched `lms/djangoapps/grades/` and found no comparison of the stored hash against the current policy; nothing refuses to reuse a grade computed under an older one.

### ORA (open response assessment)

The engine is **not in this clone**: `openassessment.*` is the external `ora2` package, `ora2==7.1.1` (`requirements/edx/base.txt:859`); edx-platform registers its apps (`openedx/envs/common.py:761-768`), routes its file upload (`lms/urls.py:228`) and sends its Celery tasks to a dedicated queue (`lms/envs/production.py:489-496`, key `lms/envs/common.py:2367`). What *is* here is the staff-grading bridge, `lms/djangoapps/ora_staff_grader/`, whose serializers state ORA's data model exactly:

| ORA holds | shape | path |
|---|---|---|
| rubric | `feedbackPrompt` + `criteria[]` | `serializers.py:75-81` |
| criterion | `{name, label, prompt, orderNum, feedback ∈ optional\|disabled\|required, options[]}` | `serializers.py:62-72` |
| **option (level)** | `{name, label, explanation, points, orderNum}` — points live on the *level*, and each level carries the prose that justifies picking it | `serializers.py:52-59`; filled example `mock/data/ora_metadata.json:11-45` |
| assessment | `{assessment_id, scorer_name/username/email, assessment_date, problem_step, feedback, assessment_scores[]}` | `serializers.py:190-204` |
| per-criterion score | `{criterion_name, score_earned, score_type}` — `score_type` is what keeps a self-mark, a peer-mark and a staff-mark on one submission distinguishable instead of collapsing into one number | `serializers.py:171-179` |
| completed grade | `gradeData = {score{pointsEarned, pointsPossible}, overallFeedback, criteria[{name, feedback, points, selectedOption}]}` | `serializers.py:291-307` |
| a grader's submission | translated to `options_selected` (criterion → option name), `criterion_feedback`, `overall_feedback`, `submission_uuid`, `assess_type ∈ {full-grade, regrade}` — a second staff mark is a first-class event, not an overwrite | `serializers.py:345-390` |

Both directions of the assessment graph are fetched — assessments *given* and *received* by a submission — documented as "Assessments can be Self, Peer and Staff" (`ora_api.py:41-53`). **Grading is leased:** `check_/claim_/delete_/batch_delete_submission_lock` (`ora_api.py:139-213`), lock states `unlocked | locked | in-progress` (`serializers.py:23-27`), lease expiry `ORA_PEER_LEASE_EXPIRATION_HOURS` and `ORA_STAFF_LEASE_EXPIRATION_HOURS`, both 8 (`lms/envs/common.py:2372-2380`). Two graders cannot hold one essay, and a crashed grader's claim expires. The learner sees the same rubric the grader does: `InitializeView` reads the ORA block — rubric included — straight out of the modulestore (`ora_staff_grader/views.py:110-116`); the surface is authenticated (`:64-75`) and behind a per-course flag (`:96-105`).

**No AI-assisted step exists in this repository.** `openai|ai_coach|ai_assisted|ora_coach` → 0 matches across `*.py`. The only course-level ORA knob is `force_on_flexible_peer_openassessments` (`xmodule/course_block.py:1002`).

## 3. Enrolment and money

- **Roles:** one row per (user, org, course, role) — `CourseAccessRole` (`common/djangoapps/student/models/user.py:1084-1103`); blank `course_id` = org-wide. Vocabulary: `staff`, `limited_staff`, `instructor`, `finance_admin`, `sales_admin`, `beta_testers`, `library_user`, `ccx_coach`, `data_researcher` (`common/djangoapps/student/roles.py:742-815`).
- **Enrolment:** one row per (user, course) — `CourseEnrollment` (`common/djangoapps/student/models/course_enrollment.py:294`) with `is_active` (`:326`) and `mode` (`:330`), every change written to a history table (`:333-338`). Un-enrolling flips `is_active`; the row survives. Entry point `add_enrollment(username, course_id, mode, is_active, …)` (`openedx/core/djangoapps/enrollments/api.py:202`), which validates the mode before creating anything.
- **The access key is an email, not an account.** `CourseEnrollmentAllowed` (`course_enrollment.py:1611`) holds `{email, course_id, auto_enroll, user}`, where `user` is filled by whoever enrols through it first and then never changes — explicitly so a student cannot change e-mail and enrol many accounts from one invitation (`:1613-1633`, `:1643-1656`).
- **What edX sells is a mode, not a course.** `CourseMode` (`common/djangoapps/course_modes/models.py:44`) carries `mode_slug` (`:61`), `min_price` (`:69`, commented as simply "the price"), `currency` (`:72`), an upgrade deadline `_expiration_datetime` (`:79-88`) and a `sku` documented as "the SKU of this mode in the external ecommerce service" (`:117-126`). Slugs: `honor`, `professional`, `verified`, `audit`, `credit`, `masters`, `executive-education`, `paid-executive-education`, `unpaid-executive-education`, `paid-bootcamp`, `unpaid-bootcamp` (`:164-175`).
- **A second layer sells a course, not a run.** `CourseEntitlement` (`common/djangoapps/entitlements/models.py:154`) — `course_uuid` (`:162`), `order_number` (`:176`), `refund_locked` (`:177`), `unique_together ('course_uuid','order_number')` (`:183`), and a policy deciding refundable / regainable / redeemable (`:236-252`). Buy once, choose a run later.
- **Payment is out of process, and the in-repo app is being deleted.** `lms/djangoapps/commerce/README.rst:1,7,9` marks it *Maintenance* / *Deprecate*, replaced by `github.com/openedx/ecommerce` (`:11`). The LMS's money verbs are HTTP: create a basket from a SKU with `checkout: True` (`lms/djangoapps/verify_student/views.py:714-731`), read an order back (`lms/djangoapps/commerce/api/v1/views.py:72-95`), statuses `Open | Fulfillment Error | Complete` (`lms/djangoapps/commerce/constants.py:4-8`).
- **Paid access is enforced inside the content tree.** With content-type gating on, every block satisfying `graded and has_score and weight != 0` gets a partition restriction to the `full_access` group (`openedx/features/content_type_gating/block_transformers.py:74-92`); audit learners sit in `limited_access` (`openedx/envs/common.py:1826-1829`, `helpers.py:17-24`), and the subsection renders a paywall fragment in place of the problem (`content_type_gating/services.py:34-47`), stored by the sequence as `gated_sequence_paywall` (`xmodule/seq_block.py:261`, `:415-425`, `:581`).
- **Refusal is typed, not boolean.** `check_course_access` (`lms/djangoapps/courseware/courses.py:163-231`) runs `has_access` (`courseware/access.py:141`) → authentication → enrolment → plugin priority filters → survey, then lets staff through regardless (`:225-231`). Every denial is an object with an `error_code`, a `developer_message` and a `user_message` (`courseware/access_response.py:11-40`): `unfulfilled_milestones` (`:168`), `not_visible_to_user` (`:185`), `incorrect_user_group` (`:227`), `enrollment_required` (`:256`), `authentication_required` (`:276`).
- **Prerequisites come in two flavours:** course-level `pre_requisite_courses` (`xmodule/course_block.py:385`, resolved in `common/djangoapps/util/milestones_helpers.py:158-168`) and subsection-level milestones with `min_score` / `min_completion` (`openedx/core/lib/gating/api.py:236-261`).

## 4. Certificates, and how a third party checks one

- **The record.** `GeneratedCertificate` (`lms/djangoapps/certificates/models.py:169`), one per (user, course) (`:258`), holding `verify_uuid` — 32 hex chars, indexed (`:231`) — plus `grade`, `mode`, `name`, `status` (`:235`), and `download_url` / `download_uuid` / `error_reason` kept only as documented remnants (`:241-245`). Its own docstring warns that this `grade` is **not** the source of truth and points at `PersistentCourseGrade` (`:183-186`). PDFs are dead by ADR: only web certificates can be generated or viewed (`docs/decisions/003-web-certs.rst:15-21`).
- **Eligibility is decided first.** `generate_certificate_task` (`certificates/generation_handler.py:38`) branches allowlist vs regular (`:163-186`): not a CCX course, not a beta tester, a passing grade (`_is_passing_grade`, `:393`), then `_can_generate_certificate_common` (`:192-207`) — not on the invalidation list, has an enrolment, and a certificate-eligible mode, which means "all modes other than `audit`" (`common/djangoapps/course_modes/api.py:20-30`).
- **Generation stamps the inputs it used.** `_generate_certificate` (`certificates/generation.py:57`) takes grade and mode as *parameters* precisely so the certificate reflects the values that decided eligibility (`:61-63`), and **reuses an existing `verify_uuid`** so the learner's URL survives re-issuance (`:70-75`).
- **The third-party check is one public URL and a 32-hex lookup.** `/certificates/<32 hex>` (`certificates/urls.py:26-31`) → `render_cert_by_uuid` (`certificates/views/webview.py:446-457`), which carries **no** auth decorator — the preview view directly above it is `@login_required` (`:438-439`) — and does `GeneratedCertificate.eligible_certificates.get(verify_uuid=…, status=downloadable)`, else 404. The URL is derived, never stored: `get_certificate_url` → `_certificate_html_url` → `reverse('certificates:render_cert_by_uuid')` (`certificates/utils.py:69-83`, `:95-101`). The ADR gives operators the recipe by hand: base URL + `/certificates/` + `verify_uuid` (`003-web-certs.rst:78-88`).
- **Revocation is a second table, not a deleted row.** `CertificateInvalidation` (`models.py:626`) records the certificate and `invalidated_by`; `has_certificate_invalidation` (`:688`) blocks regeneration; `invalidate()` fires `COURSE_CERT_REVOKED` (`:374-409`). Status vocabulary is `CertificateStatuses` (`certificates/data.py:15-58`), where `unavailable` = "Certificate has been invalidated" (`:34`) and `NON_REFUNDABLE_STATUSES` ties certificate state to refund eligibility (`:68-69`). The default manager silently drops audit-track rows (`models.py:127-148`).
- **There is no signature on the document.** Validity means "the issuing platform's database says this uuid is `downloadable`, and the platform is reachable." The signature-*shaped* elements are the platform's own config: signatories live in the course block's `certificates` dict (`xmodule/course_block.py:668-674`), read by `get_active_web_certificate` (`certificates/api.py:453-463`), with templates matched per org / mode / language (`:466-494`). A second external layer exists: grades are pushed to the separate Credentials service (`openedx/core/djangoapps/credentials/tasks/v1/tasks.py:54`, `:101`, `:154`) and read back over its API (`openedx/core/djangoapps/credentials/utils.py:19-37`, `:69`).
- **Ours, by contrast.** We serve an OB 3.0 / VC 2.0 document with a `DataIntegrityProof` ([[04-Signer-Service/S1 - The credential document]]) and two Bitstring Status Lists derived from chain state — `revocation` from `attestation.revocationTime`, `suspension` from the platform's issuer delisting ([[04-Signer-Service/S3 - Two status lists]]). Our page reads `credentialsOf` / `statusOf` straight off the resolver (`web/src/lms.ts:375-424`), so a third party depends on an RPC, not on our server being up or on our database agreeing with itself. Both systems give free, wallet-less public verification; the difference is who has to be honest for it to work. The honest counterweight: **we have never run a third-party validator against our document** — `vault/08-Results/01 - Evidence and Limits` records `❌ "our credential is compatible with the 1EdTech validator" — Never run`. edX needs no such test because the verifier *is* the issuer's own page. That is not a virtue to copy, and until an outside validator agrees with us our claim is narrower in practice than theirs.

## 5. What Lencana has that Open edX does not

*By design:*

- **The issuer is not the platform.** Everything above — grade, mode, price, certificate, invalidation — is one database owned by the LMS. Ours separates them by shape: the manifest names an issuer with its own `controllerUrl` and EOA (`web/src/manifest.ts:30-38`, `:140-148`), and the address recorded on chain as `attester` is the agent's, not the broadcaster's, because `onAttest` gates the attester and not `msg.sender` ([[04-Signer-Service/S4 - Delegated issuance]]). edX has no analogue: the platform's Celery worker both decides and records (`generation_handler.py:38`).
- **Revocation and delisting are two facts, both readable without us** — permanent issuer cancellation vs recoverable platform distrust, in two lists so a standard verifier cannot misread one as the other ([[04-Signer-Service/S3 - Two status lists]], [[Concepts/Issuer Delisted vs Revoked]]). edX collapses this into `status` strings on a row only it can read.
- **Paid *machine* verification.** Their paid path sells a mode to a human through an external ecommerce service; there is no paid machine-readable read. Ours answers `402` and settles through a split contract ([[04-Signer-Service/S6 - x402 paid verification]], [[02-Contracts/C3 - SettlementSplit]]).

*By code:*

- **`rubricHash` printed into the credential.** `canonicalPolicy` commits to criteria, weights, `passMark`, `validDays`, prereq, quiz answer keys and essay rubrics (`web/src/manifest.ts:53-100`); its short form lands in `achievement.criteria` (`web/src/manifest.ts:126-128`, surfaced as `Score.rubricHash` / `rubricRef` at `web/src/score.ts:47-48`; [[05-Course-Content/K2 - The issuer manifest and rubricHash]]). edX hashes a narrower object and prints it on nothing.
- **`BELUM_LENGKAP` as a third verdict with `total: null`** (`web/src/score.ts:39-47`; [[05-Course-Content/K4 - Scoring without the platform deciding]]). edX's `AssignmentFormatGrader` inserts placeholder zeros for assignments that do not exist yet (`xmodule/graders.py:300-302`) — exactly the conflation of "no evidence" with "scored zero" that we refuse, because our number leaves under a key that is not ours.
- **A negative control on the model judge** ([[04-Signer-Service/S5 - Grading and the model judge]], [[Concepts/Negative Control]]). They have no AI step in this repository to control.
- **Wallet-less verification that reads the chain, not our database** (`web/src/lms.ts:375-424`).

## 6. What Open edX has that Lencana lacks

*Design gaps — never decided:*

- **An enrolment record at any level.** `btnEnroll` is a translated string with no handler (`web/src/i18n.ts:189`, `:665`, `:1238`; no other occurrence under `web/src`). Theirs is one row with `is_active`, `mode` and full history (`course_enrollment.py:294-338`). The open question is not the row but what an enrolment *means* when there is no account — [[11-Refactoring/RF5 - Enrollment and the Paid Path]].
- **Modes / tracks.** No notion of a paid and a free view of one course, and no upgrade deadline.
- **A gradebook.** They store per-subsection earned/possible, first-attempted and the visible-block set; we store `{done, kind, score, attempts, draft, at}` per lesson in `localStorage` (`web/src/progress.ts:19-30`). Design question: can a server-side gradebook coexist with our position that progress is *not* evidence (`web/src/progress.ts:3-11`)?
- **Leasing a submission to a grader** — lock, three states, 8-hour lease, batch unlock (`ora_api.py:139-213`). We have one judge and no concurrency, so no lock; a human-mentor path would need one.
- **Per-attempt history and a grading-method choice.** They keep every attempt and let the author pick last / first / highest / average (`capa_block.py:94-101`, `:296-307`); we keep `attempts: number` and the last score (`web/src/progress.ts:23-24`), and `computeScore` means every quiz taken (`web/src/score.ts:57-88`).
- **Rubric levels with prose.** Their option is `{name, label, explanation, points}` (`serializers.py:52-59`); our `RubricItem` is `{label, max}` (`web/src/content.ts:60`) — a weight, not a scale. Nearest equivalent is `Essay.guidance`, a course-wide list of what will not be accepted (`web/src/content.ts:67`), which our judge does receive.
- **Typed access refusals.** They return an `error_code` plus separate developer and user messages for every reason (`access_response.py:11-40`); we render "not found" and "not configured".

*Implementation gaps — decided, not built* (all logged in [[11-Refactoring/RF1 - Consumer Readiness Audit]]): no enrolment handler (`btnEnroll` unreferenced) · no payment step · no mentor or assistant anywhere · wallet-connect only · progress in `localStorage` · no demo-vs-real separation · the learning surface is not reachable from the navigation — `web/index.html:44-49` links `#/`, `#/courses`, `#/submit`, `#/verify`, `#/portfolio`, `#/agent-hub`, while the `#/learn` router exists and works (`web/src/lms.ts:441-460`).

## 7. What we deliberately do not take

| not taken | reason |
|---|---|
| Django + XBlock runtime, the lms/cms two-process split | Buys draft/publish and field inheritance at the cost of a server, a Mongo modulestore and a Celery fleet — and puts the platform back in the middle of every decision, the one thing our architecture exists to avoid. Also breaks our limits sheet outright: the signer has no public URL and the facilitator is us ([[08-Results/01 - Evidence and Limits]]). |
| Studio as an authoring surface | Our authoring is a typed module audited by `npm run probe` (`web/src/content.ts:187-260`). A WYSIWYG editor moves policy authorship from a reviewed file into a database row, and `rubricHash` would then need a signing workflow we do not have. |
| The microservice split (ecommerce, credentials, catalogue, ora2, completion) | Their seams exist to scale an organisation; ours exist so a verifier need not trust us. Same word, different reason — copying the cut would be cargo cult. |
| `grading_policy_hash` as `b64(sha1(json.dumps(...)))` | Right idea, weaker primitive. We already have keccak over an explicit field-by-field canonicalisation that states what it drops and adds, and admits it is not JCS or RDFDS (`web/src/manifest.ts:22-26`, `:49-52`). |
| PDF certificates and their remnants | Their own ADRs say to delete them (`003-web-certs.rst:15-21`, `certificates/models.py:241-245`). |
| Content-type gating as a paywall inside the content tree | Charging for graded content is defensible; rendering a fragment in place of a problem couples money to the reading path. Our position is that verification stays free and wallet-less, visibly ([[11-Refactoring/RF5 - Enrollment and the Paid Path]]: "If we ever charge for both, we are charging for truth"). |
| Their certificate verification model | A uuid that is unguessable but not a commitment, served by the issuer's own web app, with validity equal to a database row plus uptime. It works at their scale and is exactly the property we were built to remove. |
| Anything about their front end | No page, template, component or navigation pattern from `lms/templates`, `cms/templates` or the MFEs is a source for us.
